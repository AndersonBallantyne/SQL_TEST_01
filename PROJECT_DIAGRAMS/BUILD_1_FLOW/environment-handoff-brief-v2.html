01

Audit Findings

Three discrepancies surfaced by reading the actual files and running commands against the live containers — not by re-reading Rev. 1's claims.

Finding 1 — Credentials were hardcoded and committed, not read from .env Resolved
Symptom
Rev. 1 stated: "Moved passwords into a Git-ignored .env; compose reads them via ${VAR} substitution." Reading docker-compose.yml directly showed literal values instead.
Root cause
POSTGRES_PASSWORD: REDACTED_PG_DEV_PASSWORD and MSSQL_SA_PASSWORD: "REDACTED_MSSQL_DEV_PASSWORD" were hardcoded in the compose file from the very first commit (d80d058) and updated in cleartext again in 2ef7dae. .env / .env.example existed but were never wired in — dead scaffolding.
Impact
Two real, working passwords sat in plaintext in git history the entire time.
Fix
Compose now references ${POSTGRES_PASSWORD} / ${MSSQL_SA_PASSWORD}; both values rotated in .env.
Finding 2 — seed.sql was not actually idempotent Resolved
Symptom
Rev. 1 stated: "Idempotent seed.sql (TRUNCATE ... RESTART IDENTITY on PG)." The file contained two bare INSERT blocks and no reset statement at all.
Root cause
The reset logic described in the doc was never written into the file.
Impact
A second run would violate the UNIQUE(email) constraint on customers and fail outright.
Fix
Added TRUNCATE TABLE orders, customers RESTART IDENTITY CASCADE; ahead of the inserts.
Finding 3 — SQL Server identity reseed reproduced the exact "shifted by one" bug Rev. 1 had already logged Resolved
Symptom
Restoring the DBCC CHECKIDENT RESEED calls (removed by the untested commit e6151a0 "Trying to reset PASS") to fix Finding 2's SQL Server counterpart reintroduced a live bug on the very first run against a fresh volume.
Root cause
SQL Server has a documented quirk: DBCC CHECKIDENT (..., RESEED, 0) on a table that has never held a row makes the next insert start at 0, not 1. seed_mssql.sql's orders insert hardcoded customer_id literals (1, 2, 3) — the exact pattern Rev. 1's own troubleshooting log names as the root cause of "JOIN pairings shifted by one."
Impact
On a freshly recreated volume, every order attached to the wrong customer (order id 1 landed on Alan Turing instead of Ada Lovelace).
Fix
Rewrote the orders insert to join customers by email instead of a positional ID literal — Rev. 1's own stated lesson ("prefer looking up FKs by a stable key"), now actually implemented. Correctness no longer depends on identity-reseed behavior at all.

seed_mssql.sql — reseed restored, FK lookup fixed

Before
DELETE FROM orders;
DELETE FROM customers;

GO
INSERT INTO orders
  (customer_id, product, amount)
VALUES
  (1, 'Keyboard',     79.99),
  (1, 'Monitor',     249.00),
  (2, 'Mouse',        29.50), ...
After
DELETE FROM orders;
DELETE FROM customers;
DBCC CHECKIDENT ('customers', RESEED, 0);
DBCC CHECKIDENT ('orders', RESEED, 0);
GO
INSERT INTO orders (customer_id, product, amount)
SELECT c.id, v.product, v.amount
FROM (VALUES
  ('ada@example.com',  'Keyboard',  79.99),
  ('ada@example.com',  'Monitor', 249.00),
  ('alan@example.com', 'Mouse',    29.50), ...
) AS v(email, product, amount)
JOIN customers c ON c.email = v.email;
