01

What Was Built

A hand-rolled tool-use loop — no agent framework — that answers plain-English questions about the appdb Postgres database by discovering its own schema and writing its own SQL.

The agent never has standing knowledge of the database's tables or columns. Given a question, it calls list_tables and describe_table to find out what exists, then writes and runs a SELECT query with run_sql_query, then answers in plain English. The loop keeps dispatching tool calls — one model turn can trigger several — until the model stops asking for tools or a 10-turn safety cap is hit.

Trust boundary

Unchanged in shape from the plan in Handoff Brief v2, now actually implemented and verified rather than sketched:

LLM API

Proposes SQL via tool calls. External, untrusted. Cannot execute anything itself.

→

Agent (Python)

The gate. Rejects any non-SELECT statement before a connection even opens. Runs inside Docker.

→

appdb_reader role

SELECT-only grants at the database layer. Physically cannot write, even if the Python guard were bypassed.

Build Journey

Six phases, in order, each one a working checkpoint before the next began — plus a hardening pass after Phase 6 surfaced real bugs under closer testing.

PhaseDelivered
1Python connects to appdb via psycopg, runs one hardcoded query, prints rows. Proves the driver and credentials work before anything agentic enters the picture.
2First raw Anthropic API call (api_test.py) — no tools yet. Establishes the client, reads content blocks, stop_reason, and token usage.
3Hand-wired tool-use loop: the SQL executor becomes a registered tool, a single fixed round-trip (question → tool call → result → answer).
4Schema discovery added (list_tables, describe_table); the fixed round-trip is generalized into a while loop that keeps dispatching tool calls until the model is done — required once discovery meant more than one tool call per question.
5Hardening: the appdb_reader read-only role, a Python-side SELECT-only guard, per-query timestamped logging, and graceful is_error tool-result handling so a blocked action doesn't crash the loop.
6Containerized as a third docker-compose service. DB host switches from 127.0.0.1 to the internal service name postgres — same Docker network as the database, no port exposure needed for the agent itself.
hardening passCloser testing after Phase 6 surfaced three real bugs (Section 03) — fixed, and Build 1 was not actually complete at the Phase 6 commit despite that phase's diagram originally claiming so.
03

Hardening-Pass Findings

Bugs surfaced by testing the running system harder, not by inspection — the pattern this project has followed since the environment audit in Handoff Brief v2.

Finding 1 — Only the last tool call in a multi-tool turn ever got a result Resolved
Symptom
When the model called more than one tool in a single turn, only the final tool_use block in that turn received a matching tool_result.
Root cause
The try/except wrapping each tool dispatch was indented one level too shallow — sitting outside the for block in response.content: loop instead of inside it — so the append only ran once, for whichever block the loop last landed on.
Impact
The Anthropic API requires exactly one tool_result per tool_use from the prior turn. A missing one broke the next API call outright — a real failure mode, not a cosmetic one.
Fix
Moved the try/except back inside the loop; re-verified live against a question that genuinely required more than one tool call in a turn.
Finding 2 — No upper bound on the tool-use loop Resolved
Symptom
The loop was while True, exiting only on stop_reason != "tool_use" — nothing capped how many tool-call round-trips a single question could trigger.
Root cause
No ceiling was added when the loop was generalized in Phase 4; single-tool-call testing never exercised the gap.
Impact
An unusual exchange could loop indefinitely, accumulating API cost with no natural exit.
Fix
MAX_TOOL_TURNS = 10, enforced via while turn < MAX_TOOL_TURNS / else. Verified live by temporarily lowering the cap to 1 and confirming a clean "Stopped after reaching the 1-turn limit." message — no crash, no silent hang.
Finding 3 — An Anthropic API failure would crash with a raw traceback Resolved
Symptom
client.messages.create(...) had no error handling at all.
Impact
A transient failure — rate limit, timeout, momentary outage — would surface as an unhandled Python exception instead of a usable message.
Fix
Wrapped the call in try/except anthropic.APIError; prints the error and exits the loop cleanly instead of crashing.
Finding 4 — A diagram fix regressed because it was verified against the wrong artifact Resolved
Symptom
Phase 4 and Phase 6's checkpoint diamonds were overflowing their border again, despite this exact overflow bug already having been found and fixed once earlier in Build 1.
Root cause
The earlier round of fixes was confirmed by eye against rendered PNGs. That's the right instinct, but it wasn't paired with re-checking that every SVG/HTML source file actually matched what the PNG showed — one diagram's source never picked up the fix that its own rendered output appeared to confirm.
Impact
Cosmetic only — no functional risk. Included here because the lesson generalizes: a visual or behavioral fix is only confirmed once the artifact a user will actually open is the one that got checked, not a stand-in for it.
Fix
Shortened the offending question text on both diagrams; re-verified every diagram in the set by rendering and inspecting the PNG again, not by trusting the diff.

Known Limitations & Open Items

Deliberately out of scope for Build 1, or carried forward unresolved — worth knowing before extending this spine.

No conversation persistence

Every run answers one question and exits — there's no memory of prior questions across invocations. Fine for Build 1's scope; worth a decision before any build that implies multi-turn use.

The SQL guard is a prefix check, not a parser

sql.strip().upper().startswith("SELECT") blocks the obvious cases but isn't a real SQL parser — the database role's actual privilege boundary is what really enforces safety here; the guard is the cheaper, faster first line of defense, not the last one. Worth knowing if this pattern gets reused somewhere the DB-level protection isn't also present.

No automated test suite

Every verification in this build (Section 04) was manual and interactive. Nothing runs under pytest or in CI yet — that's explicitly Build 5's job ("Live deployment with CI"), not a Build 1 gap to backfill now.

Carried over from Handoff Brief v2 — old cleartext passwords still in git history

The two original hardcoded passwords from the environment's first two commits (d80d058, 2ef7dae) are still readable in history. Rotation neutralized them going forward; they were never purged. Low risk while the repo stays local — purge with git filter-repo before any public push, as Rev. 2 already recommended.

Phase 1's shape, as already planned: pick a genuinely messy raw source, land it completely unmodified in a raw staging table, write the ingestion script, then verify the row count matches the source exactly. No transformation yet — that's deliberately a later phase.

Raw source

A CSV with real-world messiness — inconsistent casing, whitespace, mixed formats. The messiness is the point; nothing gets cleaned here.

→

Ingestion script

Reads the file, loads rows into the staging table unmodified. This is the E and the L — no T yet.

→

raw.<name> table

TEXT columns, no constraints, mirrors the source shape exactly. Correctness is measured by row count and spot-checked messiness, not by cleanliness.
