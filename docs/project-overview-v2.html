SQL_TEST_01 · Project Overview

A Database Agent That Checks Its Own Work

This is a natural-language interface to a real PostgreSQL database. Ask a question in plain English, and an agent writes the SQL, runs it through a read-only role, and answers strictly from what the query returned. A second, independent agent then checks that answer against the same evidence before it's shown — an overreaching or unsupported claim gets flagged, not silently trusted.

The system runs end-to-end: a live Docker Compose stack, a real data pipeline, a chat interface, continuous integration, and an automated test suite — all currently working, not sketched out for later.

What it does

  • Answers questions in plain English by writing and running its own SQL against a real PostgreSQL database, behind a role that can only ever SELECT.
  • Finds thematically related results with no exact keyword match, using pgvector semantic search over the underlying data.
  • Answers questions about its own build history and status the same way — semantic search over the project's own documentation, kept current automatically as the project grows.
  • Persists computed results for reuse in a scratch workspace, isolated to its own database role and schema, with age-based visibility into what's been left behind and a UI-only path to remove it.
  • Runs as a working chat application — a Streamlit front end with persistent, tiered conversation memory and full transparency into every tool call an answer relied on.

What makes it stand out

  • Self-verification. Every tool-backed answer is checked by an independent second agent against the actual evidence gathered for it, with a visible pass/fail badge and a plain-English reason — not a claim of correctness, a check of it.
  • Full cost observability. Every tool call and API turn is logged; token usage is tracked per question and, where it matters, per individual tool call, so a cost spike can be traced to its actual cause instead of guessed at.
  • Least-privilege data access. Two separate Postgres roles: one strictly read-only for querying, one scoped to a single schema for the agent's own writes — never an extension of read access, enforced at the database level, not just in application code.
  • CI-gated correctness. The full test suite and a dedicated evaluation harness — covering both the main agent's answers and the verifier's own judgment — run from a genuinely clean environment on every push, not just locally before a commit.
  • Incident-driven engineering. Real issues have been found through live usage after deployment, not only through planned test cases: root-caused to their actual mechanism, fixed, and re-verified against a freshly redeployed instance. Each one is documented in a standalone, public write-up — the process is visible, not smoothed over.
  • Documentation that stays current on its own. A command reference and a full commit history update as the system grows and stay in sync with the agent's own searchable knowledge base through a tracked pre-commit hook — so the agent's answers about its own project don't go stale.

How it was built

Build 1
The agent itself — a hand-rolled tool-use loop, no framework, against a read-only database role.
Build 2 / 2.5
A real raw-to-clean ETL pipeline from an actual equipment-checkout export, plus a writable scratch schema scoped to its own role.
Build 3 / 3.5
Semantic search over the data, then extended to the project's own documentation.
Build 4
Structured tool-call logging, an evaluation harness, and a metrics rollup.
Build 5
Public repository, continuous integration, and a real mid-build data-anonymization pivot.
Build 6
The Streamlit chat front end, with persistent, tiered conversation memory.
Build 7
The verifier — a second agent that checks every answer against its own tool evidence before it's shown.

Every claim above is backed by running code and a public commit history, not a plan for one — whether the context is evaluating a candidate or scoping a contractor, what's described here can be inspected directly: the source, the tests, the CI runs, and the incident write-ups documenting what went wrong along the way and how it was actually fixed.
