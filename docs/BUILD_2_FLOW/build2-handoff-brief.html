What Was Built, and Why

Build 1 gave the agent a database to query, but that database was hand-seeded toy data (four customers, five orders). Build 2 gives it something real: a genuine equipment-checkout export, landed unmodified, then deliberately transformed in a separate, later step — the classic ELT split, done as two distinct schemas (raw then clean) rather than one script that ingests and cleans in the same breath.

The two-schema split is the core design decision: raw.allocations is all-TEXT, no constraints, mirroring the source file exactly — its entire job is preserving what the source actually said before any decision gets made about what it means. clean.allocations is where those decisions happen: real types, a generated column, deliberate NULL handling. Keeping them as two tables (not one, cleaned in place) means the original import is always available to re-derive from if a transformation decision turns out wrong later.

1The Raw Ingestion Layer

Goal: land a genuinely messy real-world CSV completely unmodified in a staging table, and verify the row count matches the source exactly. No transformation yet — that's deliberately a later phase.

The source: a real equipment-checkout export (ALLOCATION-export-Oct_2024-2025.csv, 1,535 rows) from an actual institution, kept outside this repo. Its Patron Email column was already exported as domain-only (e.g. @artschool.edu) rather than full addresses — a privacy choice made at export time, not something this project added. The real institution's domain was later masked to the fictional artschool.edu before this became a public-facing portfolio piece (see project_agent-roadmap.md memory for that masking pass in full).

004_raw_schema.sql (originally raw_schema.sql, renamed when SQL files were numbered)CREATE SCHEMA IF NOT EXISTS raw;

DROP TABLE IF EXISTS raw.allocations;

CREATE TABLE raw.allocations (
    allocation_id     TEXT,
    patron_department TEXT,
    patron_email       TEXT,
    renewal_count      TEXT,
    actual_start        TEXT,
    scheduled_end       TEXT,
    actual_end           TEXT,
    duration             TEXT,
    resource_count       TEXT,
    summary              TEXT
);

GRANT USAGE ON SCHEMA raw TO appdb_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA raw TO appdb_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA raw GRANT SELECT ON TABLES TO appdb_reader;
Every column is TEXT, on purpose. Nothing here is cleaned or coerced — not even obviously numeric fields like renewal_count. Deciding what a value means (a number? a timestamp? a real NULL?) is explicitly Phase 2's job, not this one's. Mixing the two would make it impossible to tell, later, whether a "clean" value reflects the source or an ingestion-time assumption.

Why csv.DictReader, not pandas, for ingestion specifically: csv.DictReader guarantees every field arrives as a plain string, with nothing silently type-coerced. Pandas' automatic type inference is exactly the kind of decision this layer is designed to defer to Phase 2. Pandas still gets used — one phase later, for profiling.

Verified live: SELECT count(*) FROM raw.allocations; → 1535, matching the source CSV's row count exactly.

Goal: understand the raw data's actual messiness before deciding the clean schema, then write the transformation that turns text into real types — deliberately, not by pandas' automatic inference.

What profiling actually found, and why each finding mattered: patron_department had real blank strings mixed with real values — not garbage, a genuine "not applicable" case that needed to become a true NULL, not stay as ''. All three date columns parsed cleanly against one exact format (MM/DD/YYYY H:MM AM/PM) with zero failures. The stored duration column's values matched a freshly computed actual_end − actual_start exactly — meaning clean.allocations could compute duration instead of trusting a redundant stored field, closing off an entire class of future drift between the two.
005_clean_schema.sqlCREATE SCHEMA IF NOT EXISTS clean;

DROP TABLE IF EXISTS clean.allocations;

CREATE TABLE clean.allocations (
    allocation_id        TEXT PRIMARY KEY,
    patron_department    TEXT,
    patron_email_domain  TEXT NOT NULL,
    renewal_count         INTEGER NOT NULL,
    actual_start           TIMESTAMP NOT NULL,
    scheduled_end           TIMESTAMP NOT NULL,
    actual_end               TIMESTAMP NOT NULL,
    duration_seconds          INTEGER GENERATED ALWAYS AS
        (EXTRACT(EPOCH FROM (actual_end - actual_start))::INTEGER) STORED,
    resource_count             INTEGER NOT NULL,
    summary                     TEXT
);

GRANT USAGE ON SCHEMA clean TO appdb_reader;
GRANT SELECT ON ALL TABLES IN SCHEMA clean TO appdb_reader;
ALTER DEFAULT PRIVILEGES IN SCHEMA clean GRANT SELECT ON TABLES TO appdb_reader;
duration_seconds is GENERATED ALWAYS AS (...) STORED, not a plain inserted column. Postgres computes and locks it from actual_start/actual_end in the same row — structurally impossible for it to drift out of sync, unlike the raw layer's separately-stored duration field that profiling proved (for this dataset) happened to already agree.
transform.pyDATE_FORMAT = "%m/%d/%Y %I:%M %p"

record["patron_department"] or None is the one deliberate cleaning decision in this whole script. Python treats an empty string as falsy, so a blank department becomes a real SQL NULL instead of staying an empty string — the exact gap profiling surfaced. Every other field is a direct type conversion (int(), datetime.strptime()), not a judgment call.

Verified live: SELECT count(*) FROM clean.allocations; → 1535, matching raw.allocations exactly. patron_email_domain distinct values: @inside.artschool.edu (946), @artschool.edu (571), @alumni.artschool.edu (9), @gmail.com (9) — real categorical signal, confirming the domain-only export wasn't lossy for this dataset's purposes.

3Agent Integration & Data Quality

Goal: let the agent actually see clean.allocations, and codify what "correct" means for that table as real, automated tests — the first automated test suite in this project.

tools.py — schema discovery widenedWHERE table_schema IN ('public', 'clean')
Deliberately not raw. appdb_reader's grants extend across public, raw, and clean, but tools.py's schema-discovery query only surfaces public and clean to the agent. raw stays internal-only — a real distinction between what a role is permitted to touch and what the agent is actually told exists.

Real gap found and fixed mid-phase: the first cross-table question exposed a real self-correction moment — the model tried an unqualified table name, got a genuine Postgres error back, and retried with the clean. prefix on its own without being told to. Not a bug, but the first live proof that graceful error recovery (not just error handling) was actually working end to end.

test_data_quality.pyimport pandera.pandas as pa

CLEAN_SCHEMA = pa.DataFrameSchema({
    "allocation_id": pa.Column(str, unique=True, nullable=False),
    "patron_department": pa.Column(str, nullable=True),
    "patron_email_domain": pa.Column(str, nullable=False),
    "renewal_count": pa.Column(int, pa.Check.ge(0), nullable=False),
    "resource_count": pa.Column(int, pa.Check.ge(0), nullable=False),
    "duration_seconds": pa.Column(int, pa.Check.ge(0), nullable=False),
})

def test_raw_row_count():
    assert len(_query("SELECT * FROM raw.allocations")) == 1535

def test_clean_row_count_matches_raw():
    raw = _query("SELECT COUNT(*) AS n FROM raw.allocations")
    clean = _query("SELECT COUNT(*) AS n FROM clean.allocations")
    assert raw["n"][0] == clean["n"][0]

def test_clean_department_has_real_nulls():
    clean = _query("SELECT patron_department FROM clean.allocations")
    assert clean["patron_department"].isna().sum() > 0

def test_clean_schema_types_and_constraints():
    clean = _query("SELECT allocation_id, patron_department, patron_email_domain, "
                   "renewal_count, resource_count, duration_seconds FROM clean.allocations")
    CLEAN_SCHEMA.validate(clean)
Why pandera, not scattered asserts: DataFrameSchema declares an entire table's expected shape — types, nullability, value constraints — as one piece of data rather than a pile of ad hoc checks. test_clean_department_has_real_nulls is the direct regression guard for Phase 2's blank→NULL decision: if a future change ever silently reverted to storing empty strings, this test would fail loudly instead of the gap going unnoticed.

Result: all 4 tests passing on first run, connecting as appdb_reader (not the owner role) — the same read-only credential the agent itself uses.

Known Limitations & Open Items

list_tables/describe_table as two separate calls, not one. The first real cross-table question triggered 3 separate describe_table calls in one turn — the model exploring every discovered table, not just the one the question needed. Not a bug (the agent still answered correctly, token cost negligible on Haiku-tier), but a genuine, low-priority efficiency idea: merging the two tools into one "describe everything" call would cut round-trips without changing how much schema information the model receives. Flagged for later, not fixed now — carried forward into Build 2.5's brief, still unaddressed as of that build too.
raw excluded from agent-visible schema discovery, by design. appdb_reader can technically SELECT from raw.allocations (the grant is there), but tools.py's discovery query never surfaces it to the model. Intentional, not a gap — worth remembering if a future build ever needs the agent to reason about data provenance, since today it structurally cannot see the raw layer exists.
Resolved during this build — no automated tests, at all, through Build 1. Every Build 1 verification was manual and interactive. Build 2 Phase 3's test_data_quality.py is the first automated suite in the project, establishing the pandera + pytest pattern every later build's own test suite has since followed.
