What Was Built, and Why

Every eval case built since Build 4 checks the agent's behavior offline, against a fixed set of questions run by hand. None of that infrastructure does anything once the agent is actually answering a real question live. Build 7 closes that gap: a second, narrowly-scoped agent whose only job is judging whether the main agent's proposed answer actually follows from the tool evidence gathered for it — the eval harness's "verify against ground truth" ethos, extended into runtime.

Scoped originally during a 2026-07-24 placement/portfolio-strategy discussion (not a technical gap found hands-on, unlike every other build so far) — picked over a router/supervisor alternative specifically because that tool-choice judgment call was already handled reasonably well by the main agent's own system prompt (a Build 3 design point), so a router wouldn't add real value the way a verifier does.

Nothing about the main agent's own reasoning changed in this build. The verifier is a separate agent, called after the main agent already has its answer, reading the same structured tool-call log Build 4 already produces. No changes to tools.py, the tool schemas, or SYSTEM_PROMPT.

Design Decisions

Four forks resolved in a dedicated scoping conversation before any Phase 2+ code was written.

1. The Verifier's Own Model & Prompt

The original scoping note called it "a second, cheaper agent" — worth naming directly: the main agent already runs on claude-haiku-4-5, the cheapest/fastest current-gen Claude model, so there's no smaller tier to drop to. The real cost saving is scope, not model tier: the verifier's prompt is a single bounded judgment (question + tool evidence + proposed answer → supported/unsupported), never the full multi-turn conversation history the main agent carries. Same model, narrower prompt, and a forced tool_choice so the verdict is always a structured field, never prose that needs parsing.

2. Where the Verdict Surfaces

OptionVerdict
Log only (Phase 2, built)A new log_verification() event, same shape as log_final_answer(). Zero UX risk, proves the logic works before anything user-facing depends on it.
UI trust badge (Phase 3, built)Non-blocking green/red status in the browser. Low risk since it only informs, never gates.
Blocking/retry a flagged answerDeferred, not built. Highest complexity and real risk — a verifier false-positive would become a live UX regression, not just log noise. See Known Limitations.

3. Every Turn, or Opt-In?

Full always-on doubles the API call count per question. Pure opt-in feels bolted-on rather than integral. The chosen middle ground reuses a signal that already existed rather than adding new state: skip verification when a turn made zero tool calls — there's no evidence to check an answer against if none was gathered (e.g. "What can you do?"). get_tool_calls(question_id, include_output=True) returning an empty list is the gate.

4. Phase Breakdown

Mirrors this project's established shape for every prior build: prove the mechanism standalone first (Phase 1, same pattern as search_summaries.py predating tools.py's wired version), wire it into the real system second (Phase 2), surface it to a user third (Phase 3), then a stretch phase proving the mechanism actually catches failures rather than assuming it does (Phase 4) — the same rigor Build 4's eval harness already established for the main agent, applied here to the verifier itself.

1Standalone Verifier Proof

Goal: prove the verdict logic works in isolation, before touching agent.py — same standalone-first pattern as every prior build's Phase 1.

verify_answer.py — the core judgment callVERIFIER_SYSTEM_PROMPT = """You check whether a proposed answer is actually supported by the tool evidence gathered for it. You are not answering the original question yourself and must not use any outside knowledge - judge only whether the proposed answer logically follows from the tool call inputs/outputs shown to you.

Call report_verdict with supported=true only if every claim in the proposed answer is backed by the tool evidence. If the answer contradicts the evidence, overstates it, or claims something the evidence never shows, set supported=false and explain why in reason."""

def verify_answer(user_question, answer, tool_calls):
    evidence = build_evidence_block(tool_calls)
    response = client.messages.create(
        model="claude-haiku-4-5",
        system=VERIFIER_SYSTEM_PROMPT,
        tools=[VERIFIER_TOOL],
        tool_choice={"type": "tool", "name": "report_verdict"},
        messages=[{"role": "user", "content": user_content}],
    )
    for block in response.content:
        if block.type == "tool_use" and block.name == "report_verdict":
            return block.input["supported"], block.input["reason"]

The script's CLI accepts a real question_id from logs/tool_calls.jsonl, plus an optional second argument that overrides the logged answer — one script proves both the good case (real evidence + real answer) and a deliberately-bad case (real evidence + a hand-typed wrong answer) without needing two separate scripts.

Both verdicts cite specific evidence (item names, actual query rows) in their reasoning, not generic filler — the thing that actually matters for Phase 4 to later prove wasn't a coincidence.

2Wire the Verifier Into the Agent

Goal: run the verdict automatically on real traffic, gated on the zero-tool-call rule from the scoping decisions above, without ever risking the main answer.

agent.py — the whole integration, inside ask_agent()'s success returnif response.stop_reason != "tool_use":
    log_final_answer(question_id, user_question, answer)
    try:
        evidence = get_tool_calls(question_id, include_output=True)
        if evidence:
            supported, reason = verify_answer(user_question, answer, evidence)
            log_verification(question_id, user_question, answer, supported, reason)
    except Exception as e:
        print(f"[VERIFY ERROR] {e}")
    return {"answer": answer, "error": None, "full_messages": messages, "question_id": question_id}
get_tool_calls gained an include_output flag, default False. The Phase 4 (Build 6) UI caller never needed raw tool output — only the verifier does, since judging an answer requires seeing what the tools actually returned, not just that they ran. Defaulting False means the existing UI caller and its tests are entirely unaffected by this change.
log_verification()'s entry deliberately uses answer_text, not answer, as the key. get_final_answer() already filters on "answer" in entry to find log_final_answer()'s entries — reusing that exact key on a verification entry would create a fragile dependency on write order (the final-answer entry happening to be written first) rather than a structurally impossible collision. get_verification() filters on "supported", a key only its own entries ever carry.

Bugs Found & Fixed

Two real, would-have-broken-production bugs, both caught by review before ever being run — a direct payoff of this project's standing "inspect the entry before testing" habit.

1. A one-line indentation error in agent.py that would have raised IndentationError on the very first import. The if response.stop_reason != "tool_use": line landed at 12 spaces instead of 8, one level deeper than the plain statement directly above it — Python requires the same indent level after a line that doesn't open a new block, so this wasn't just cosmetically wrong, it was a hard parse failure that would have stopped every question, not just verification.
Fixed: dedented the single line back to 8 spaces. Confirmed via a precise per-line indentation dump (not eyeballing) that every line below it was already correctly nested relative to that fix — one line was the entire bug, not a cascade.
2. The Dockerfile's COPY line never picked up verify_answer.py — same bug class as Build 4's logging_utils.py omission in Build 6. agent.py now does from verify_answer import verify_answer, but the image would have built "successfully" and then failed with ImportError the moment the container actually started, since the file was never copied in at all.
Fixed: COPY agent.py tools.py logging_utils.py app.py verify_answer.py ./. Verified directly inside the running container (not assumed from the build log) via docker exec ... ls //app/verify_answer.py and a grep confirming the container's own copy of agent.py/app.py actually has the new imports and calls.

3UI Trust Badge

Goal: surface the verdict to a human, non-blocking, matching the "log only, then UI flag" phased rollout from the design decisions above.

app.py — the whole rendering logicdef render_verification_badge(verification):
    if verification is None:
        return
    if verification["supported"]:
        st.success("✓ Verified against tool evidence")
    else:
        st.error(f"⚠ Unverified: {verification['reason']}")
Streamlit built-ins over raw HTML, for a real reason, not just convenience. A colored <span style='color:...'> via unsafe_allow_html=True was considered for exact color control — rejected because the reason text embedded inside it is LLM-generated, not trusted input, and rendering it as raw HTML would be a real (if low-probability) XSS surface if the model ever produced text that looked like a tag. st.success()/st.error() give the same green/red semantic with Streamlit's own safe text escaping and no new attack surface.

verification is fetched via the same log-as-source-of-truth pattern get_tool_calls/get_final_answer already established, threaded into round["verification"] for both freshly-asked and persisted-history rounds, and rendered right before the existing Tools Used expander in all three places an answer appears on screen.

Live-confirmed in the browser: a real question through the fully rebuilt container correctly showed the green badge. A deliberately adversarial question ("What's the total dollar value of all Nikon Z6 III equipment currently checked out?" — clean.allocations has no price column at all) produced a well-behaved answer: the agent correctly found zero active checkouts and correctly declined to invent a dollar figure, which the verifier correctly marked supported: true — a good outcome, not a missed catch, since nothing in the answer actually overreached.

Known Limitations & Open Items

Blocking/retry behavior was scoped and explicitly deferred, not built. If a real answer gets flagged supported: false today, nothing happens beyond the log entry and the red badge — the main answer is never retried, hedged, or withheld. This was a deliberate Phase 2 design-decision boundary (see Design Decisions above), not an oversight: a verifier false-positive blocking a correct answer would be a real UX regression, and that risk shouldn't be taken on until the log-only and UI-flag phases have proven the verifier trustworthy over real usage.
The red/unsupported badge was proven at the data and component layer, not forced to render live in the browser. get_verification() returning the right shape for a known-bad case, and st.error() being a standard well-tested Streamlit built-in (same reliability class as st.success(), which did render correctly live) together give strong confidence without needing to hand-craft a fake chat_rounds/log_verification pair just to force the browser render — judged not worth the more invasive test-fixture setup for a UI branch that's structurally identical to the already-confirmed green one.
Process note, kept honest rather than smoothed over: the diagram-first ordering lapsed for Phase 1. Every prior build in this project publishes a phase's flow diagram before writing its code, confirmed by the git log itself. Phase 1's diagram was built retroactively, after the code already existed and worked — caught by direct question, not self-caught. Phases 2 through 4 restored the correct order, including the full dual-verification pass (--screenshot and --print-to-pdf+pdftoppm) that Phase 1's diagram also initially skipped and had to be re-run for.
